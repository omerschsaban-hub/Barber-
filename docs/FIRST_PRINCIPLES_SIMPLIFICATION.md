# Fabrient First-Principles Simplification

This document is the decision framework for reducing product and engineering waste without weakening deterministic engineering, evidence, safety, or the Define → Analyze → Fix → Verify → Build → Release lifecycle.

## 1. DELETE

Delete or retire only after dependency/production verification:

- Duplicate mobile application surface when one mobile implementation is not required.
- Marketing/video production infrastructure from the product runtime repository.
- Obsolete repair-only and migration-only workflows after the associated migration/repair is permanently complete.
- Duplicate production-connectivity documentation; keep one canonical source.
- Decorative dashboards and metrics that do not change an engineering decision.
- Generic AI chat that does not advance an engineering job.
- Duplicate engineering-rule implementations.
- MCP aliases that expose the same backend operation without adding a meaningful workflow contract.
- Unsupported engineering-number/confidence features.
- Setup questions whose answers can be safely derived from supplied assets or defaults.

## 2. SIMPLIFY

- Keep one web product surface as the primary product.
- Keep the engineering graph, but show current action, evidence, blocker and next action by default.
- Keep expert engineering configuration, but expose safe defaults first.
- Keep full audit history, but make current release state the default view.
- Keep detailed reports, but lead with decision, reason, required action and evidence.
- Keep deterministic primitives internally, but group them behind coherent engineering workflows.
- Keep one authentication boundary and one shared engineering operation layer where possible.

## 3. AUTOMATE

- Normalize every natural-language request into a job contract: objective, inputs, constraints, evidence, allowed actions, approval gates, deliverables and completion criteria.
- Infer values from uploaded assets when safe.
- Automatically select only applicable engineering checks.
- Automatically skip irrelevant checks.
- Automatically verify bounded modifications.
- Automatically collect evidence, provenance, assumptions and blockers.
- Automatically select the next graph action when the state is unambiguous.
- Automatically prepare reports and manufacturing packages from generated evidence.
- Automatically run release gates before claiming completion.

## 4. OPTIMIZE

Only optimize after deletion and simplification:

- One implementation per engineering rule.
- One shared operation engine for UI/API/MCP.
- Reuse connections and expensive CAD parses where safe.
- Cache deterministic, content-addressed results where inputs and implementation version are unchanged.
- Index high-volume project/evidence queries.
- Avoid invoking CV, simulation or ML when prerequisites are absent.
- Minimize MCP schema and payload size.
- Measure operation latency, failure rate and cost.

## 5. USER-INPUT ELIMINATION

A user should not be asked for information Fabrient can safely derive.

### Eliminate

- Re-entering dimensions already present in CAD/STEP/PCB assets.
- Selecting individual DFM checks for a normal job.
- Confirming routine verification that is mandatory after a bounded change.
- Selecting the next engineering step when the graph has a deterministic next action.
- Repeating project constraints already stored in the job contract.
- Manually assembling reports from evidence already generated by the system.
- Choosing irrelevant tools or internal agents.

### Preserve / ask only when necessary

Ask when missing information changes engineering correctness, safety, or release eligibility. Never invent missing tolerances, measurements, material properties, machine constraints, or confidence.

## Acceptance rule

Every proposed feature or request must answer:

1. What engineering outcome does it improve?
2. Can the system derive it safely?
3. Does it change a decision or release gate?
4. Is it a duplicate of an existing capability?
5. Can the same outcome be achieved with fewer UI controls, tools, files, services or requests?

If it does not materially improve the engineering outcome, prefer deletion or deferral.
