# Fabrient PostgreSQL-first frontend architecture

## Target architecture

Vercel/Next.js remains the web delivery layer only. It is **not** the data owner.

Browser -> Next.js frontend/API boundary -> authenticated application services -> Render PostgreSQL
                                           -> Render object storage service (planned)
                                           -> Render realtime gateway (planned)
                                           -> Fabrient Engineering API
                                           -> Fabrient MCP

Supabase is retained only for authentication. No application tables, Storage buckets, or Realtime channels are authoritative in Supabase after cutover.

## Data ownership

- PostgreSQL: all application state, relational data, jobs, events, audit/provenance, agent/MCP execution state, billing references, engineering state, and realtime event log.
- Object storage: large CAD/STEP/STL/PDF/image/manufacturing artifacts. PostgreSQL stores immutable object metadata, ownership, content hash, size, MIME type, and lifecycle state.
- Realtime: PostgreSQL transactional outbox/event log + a dedicated websocket/SSE gateway. Clients subscribe through the application API; clients never connect directly to PostgreSQL.
- Supabase Auth: identity only. The frontend obtains the authenticated user/session from Supabase Auth and sends the identity/session to the Fabrient application boundary. Authorization is enforced by Fabrient against PostgreSQL tenant membership/roles.
- Vercel: static/SSR frontend delivery, not the source of truth.

## Tenant model

Every tenant-owned row must carry `organization_id` (or an equivalent principal/ownership key), with PostgreSQL foreign keys and application authorization checks. Support three workspace modes:

1. Individual — one-person workspace.
2. Startup/team — shared organization, projects, roles, invitations.
3. Enterprise — organizations, projects, teams, granular roles, audit, retention and policy controls.

## Frontend rules

1. Do not import `@supabase/supabase-js` for database, storage, or realtime operations.
2. Do not expose `DATABASE_URL` to browser code.
3. Browser calls `/api/*` or the application services; server-side code owns database connections.
4. All mutations are transactional and emit an outbox event when user-visible state changes.
5. Realtime UI consumes events from the Fabrient realtime gateway, keyed by tenant/project/resource.
6. Large files use signed object-storage URLs generated by the application server; PostgreSQL stores the artifact record.
7. Use idempotency keys for uploads, agent runs, MCP calls, manufacturing releases and billing webhooks.
8. All engineering claims remain evidence-gated; the frontend must display `blocked`, `validated`, `human_release_required`, and provenance states rather than turning incomplete execution into success.

## Cutover

1. Keep Supabase Auth active.
2. Export/migrate Supabase application data to Render PostgreSQL and verify row counts/checksums/foreign keys.
3. Move application reads to PostgreSQL.
4. Move application writes to PostgreSQL.
5. Move file objects to object storage and verify hashes.
6. Enable PostgreSQL-backed event/realtime gateway.
7. Run full frontend + MCP + engineering + flywheel acceptance tests.
8. Remove Supabase database/storage/realtime dependencies from application code.
9. Keep Supabase Auth only.

No destructive deletion occurs until the acceptance gate passes and a rollback snapshot exists.
